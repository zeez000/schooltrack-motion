# SchoolTrack Security & Production Runbook

SchoolTrack handles student identity, attendance, school-journey checkpoints, guardian relationships and vehicle location. Treat all of those as sensitive operational data.

This document describes the controls implemented by the repository and the controls an operator still must provide when deploying it.

## Security invariants

- Vehicle GPS never proves that a student is on the vehicle.
- A later checkpoint never silently creates or confirms an earlier checkpoint.
- Tenant isolation is enforced server-side by `schoolId`, not by frontend filters.
- Parents require an active guardian link.
- Teachers require an active class assignment.
- Transport staff require an active route assignment for the relevant journey direction.
- Parent access to vehicle location requires an active journey for one of their linked students.
- Device checkpoint sources come from registered device type/capability, not a client-supplied source label.
- Guardian handover requires an active guardian explicitly marked as authorized for pickup.

## Credentials and sessions

### User passwords
Passwords are hashed with Node.js scrypt and random per-password salts. Self-registration is disabled by default and is always disabled in production.

The login endpoint is throttled by both source IP and a hashed account identifier. Error text is intentionally identical for nonexistent accounts and incorrect passwords.

### Access and refresh tokens
Access tokens are short-lived signed tokens. Refresh tokens are high-entropy opaque values stored only as SHA-256 hashes.

Refresh rotation uses an atomic claim: concurrent requests cannot both rotate the same refresh session. Reuse of a previously claimed/revoked refresh token revokes the user's active refresh sessions and increments the user's token version, invalidating outstanding access tokens.

Changing a password also increments token version and revokes all refresh sessions.

### Device credentials
Device tokens are returned only at creation or explicit token rotation. Only their SHA-256 hashes are stored. Devices can be disabled by an admin.

Scanner/tablet devices have an explicit `allowedEventTypes` allowlist. GPS trackers cannot create student checkpoint events and must be bound to one vehicle before they can ingest vehicle location.

## Production environment requirements

Production startup fails if:
- the JWT secret is the development placeholder or shorter than 48 characters;
- CORS is empty or wildcard;
- a CORS origin is not an explicit HTTPS origin.

Recommended production values:
- `NODE_ENV=production`
- `ENABLE_DEV_REGISTRATION=false`
- `TRUST_PROXY=true` only when running behind the provided/known reverse proxy
- a random JWT secret generated by a cryptographically secure password generator
- unique, high-entropy PostgreSQL credentials
- explicit HTTPS frontend origin(s)

Never run the fictional seed in production. The seed refuses to run when `NODE_ENV=production`.

## Network deployment

For self-hosting, use:

```bash
docker compose -f docker-compose.prod.yml up --build -d
```

The production Compose file:
- keeps PostgreSQL on an internal-only Docker network with no host port;
- exposes the API only to the reverse proxy;
- publishes only HTTP/HTTPS through Caddy;
- applies `no-new-privileges`, drops backend Linux capabilities and applies a PID limit;
- uses Caddy for TLS termination and HSTS.

For managed hosting, preserve the same topology: public HTTPS proxy -> API -> private database.

## Resource and abuse controls

The API applies:
- JSON body-size limits;
- global API request limiting;
- stricter login/account rate limits;
- device IP and device-key rate limits;
- HTTP request/header/keep-alive timeouts;
- a maximum SSE connection lifetime;
- bounded accepted timestamps for checkpoint and GPS ingestion.

The built-in limiter is process-local. Before horizontal scaling or untrusted high-volume Internet exposure, add a shared rate limiter at the API gateway/reverse proxy (for example Redis-backed or provider-native rate limiting).

## Data minimization

Parent/student API responses deliberately omit internal device IDs, recorder user IDs, external source-event IDs and arbitrary internal checkpoint metadata.

GPS retention is controlled by `VEHICLE_LOCATION_RETENTION_DAYS`. New samples prune older samples for that vehicle. A production deployment should also run a scheduled retention task so inactive vehicles do not retain data indefinitely.

Audit logs intentionally preserve security-sensitive mutations; define a separate retention policy for them based on school/legal requirements.

## Incident actions

### Compromised user account
1. Disable the user through the school-admin user status endpoint. This revokes refresh sessions and invalidates access tokens.
2. Investigate audit records for the user.
3. Re-enable only after identity verification and password reset.

### Compromised refresh token
A detected refresh-token replay automatically revokes the session family and access-token version. Require the user to log in again.

### Compromised device token
1. Rotate the token with `POST /api/admin/devices/:deviceId/rotate-token`, or disable the device.
2. Review audit/checkpoint records associated with that device.
3. Reprovision the physical device securely.

### Compromised JWT signing secret
Replace `JWT_ACCESS_SECRET` and restart every API instance. This immediately invalidates all access tokens signed with the old secret. Also revoke active refresh sessions if user reauthentication is required.

### Suspected tenant/data exposure
Take the affected deployment out of public service if necessary, preserve logs/audit evidence, rotate credentials, determine the affected school/users/data window, and follow applicable breach-notification and child-data obligations.

## Backups and availability

Before a real-school pilot:
- enable automated encrypted PostgreSQL backups;
- test restore procedures;
- monitor `/ready`, error rate, latency, authentication failures and repeated device failures;
- alert on repeated token replay, tenant authorization failures and unusual checkpoint/GPS volume;
- provide a manual school safety process for outages. The software must not be the only method to account for children.

## Supply-chain controls

GitHub Actions runs:
- locked dependency installation;
- `npm audit --omit=dev --audit-level=high`;
- migrations and seed in test mode;
- PostgreSQL-backed backend tests;
- strict TypeScript typecheck and build;
- backend Docker image build;
- local and production Compose validation;
- frontend tests/build.

CodeQL scans JavaScript/TypeScript on main, pull requests and weekly. Dependabot checks npm, Docker and GitHub Actions weekly.

## Privacy/legal readiness

Technical hardening is not legal compliance. Before handling real children's data, define:
- school/guardian onboarding and identity-verification procedures;
- consent/notice requirements;
- access/correction/deletion handling;
- data-retention schedules;
- processor/vendor contracts;
- jurisdiction-specific child/privacy requirements;
- operational policy for staff use of GPS/checkpoint data.

## Reporting vulnerabilities

Do not publish credentials, child data, exploit tokens or sensitive reproduction data in a public issue. Prefer GitHub private vulnerability reporting if enabled. Otherwise open a minimal public issue requesting a private contact channel without sensitive details.
